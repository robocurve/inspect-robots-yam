# 0018 — RealSense capture process isolation

**Issue:** #95 · **Branch:** `fix/capture-process-isolation` · **Status:** draft (critique round 1 addressed)

## Problem

With all three camera slots on `{slot}_depth_serial`, both CAN chains report
per-motor `loss communication` at first-observation time and the i2rt robot
servers exit — two consecutive on-rig reproductions (2026-07-30, different
victim motors each time). USB, CAN integrity, bandwidth, and hardware were
ruled out at the kernel/bus level; standalone streaming of the same three
cameras at full rate alongside motor reads stayed healthy **when the cameras
ran in a separate process**.

Mechanism: the i2rt DM control loops are plain Python threads in the same
interpreter as the capture stack. The librealsense drain threads
(`_RealsenseCameraReader._drain` → `align.process` → two `np.asarray(...).copy()`
per frame per camera) plus first-observation work (resize, PNG encodes, wire
capture, rerun) contend for the GIL. A stall longer than the motor reply
deadline reads as "loss communication" — the driver can't tell "motor went
silent" from "nobody was listening." The V4L2 path has never shown this; it
does strictly less Python-side work per frame.

Fix direction (per #95): move RealSense capture out of the control process
entirely, so no camera or image work can hold the GIL the motor threads need.

## Design

### 1. New module `_capture_proc.py`: a spawn-context capture child

One child process owns **all** configured RealSense pipelines (not one child
per camera — a single child halves the process-management surface and the
per-frame work in the child is C++-dominated; it has no motor threads to
starve).

- `multiprocessing.get_context("spawn")` only. Fork is unsafe under the
  parent's live threads, and spawn is the portable behavior across the CI
  matrix (ubuntu + macos).
- **Child entry is a testable function** `_child_main(conn, spec, *,
  rs_module=None)`: `rs_module=None` triggers the lazy
  `import pyrealsense2` (that import line is the *only* pragma'd line in
  the entry; everything else is exercised in-process — see Tests). The
  module's top level imports only stdlib + numpy, keeping the
  `import-hygiene` CI job green.
- **The child receives a minimal frozen spec** (a small dataclass defined
  in `_capture_proc.py`: serials by slot, fps, shm names, frame dims) —
  not `YamConfig`. Unpickling `YamConfig` would drag the full package
  import graph into every spawn; the spec keeps the child's import set at
  stdlib + numpy and the spawn fast.
- Child responsibilities, mirroring `_RealsenseCameraReader` semantics
  exactly: serial resolution via `rs.context().query_devices()` matching
  `serial_number` *and* `asic_serial_number`, duplicate-device rejection,
  all-or-nothing open, per-camera 640×480 colour+depth streams,
  `rs.align(color)`, `depth_scale` read once, warm-up frames, then a drain
  loop publishing into shared memory.
- Open handshake over a `Pipe`: child replies `("ready", meta)` or
  `("error", message)`; the parent raises the same open-failure errors it
  does today, within `OPEN_TIMEOUT_S` (generous — real opens take seconds).
- **Parent-death safety** (the inline reader's daemon threads die with the
  process and release the cameras; the child must match that): (a) the
  child is started with `daemon=True`, so a clean parent exit reaps it;
  (b) the drain loop polls its `Pipe` end every iteration and **exits on
  EOF** — the parent end closing for *any* reason (including SIGKILL of a
  parent holding torque-enabled arms, the very #95 scenario) is the
  parent-death signal. No orphaned child may keep the cameras busy for the
  next run.
- Cooperative shutdown: parent closes its `Pipe` end and sets a stop
  `Event`, joins with the existing 2.0 s budget, then escalates
  `terminate()` → `kill()`. This *improves* on the inline reader, which
  can only leak a wedged pipeline; a wedged child is killable without
  endangering the parent.

### 2. Shared-memory frame slots with a seqlock

Per camera, one `multiprocessing.shared_memory.SharedMemory` block laid out
as: header (`seq: uint64`, `published_s: float64`, `generation: uint64`,
`depth_scale: float64`), colour `(480, 640, 3) uint8`, depth
`(480, 640) uint16`, intrinsics `(3, 3) float32`.

- **Names are stdlib-autogenerated** (`SharedMemory(create=True)`) and
  passed to the child in the spec — macOS caps POSIX shm names at 31
  chars, so no deterministic naming scheme; the Python-level
  `Process(name=...)` is for logs only (it does not retitle the OS
  process).
- **Lifetime protocol (resource_tracker-proof):** parent creates the
  blocks; child attaches and immediately **unregisters them from its own
  `resource_tracker`** (`resource_tracker.unregister(...,
  "shared_memory")`, or `track=False` where available, version-guarded) —
  otherwise the child's tracker unlinks the segments the moment the child
  exits (clean stop *or* kill escalation) on Python ≤ 3.12, breaking
  reopen and unlink; parent **unlinks the names right after the ready
  handshake** — the mappings survive, the names can never leak, and every
  reopen creates fresh blocks.
- **Seqlock, no cross-process locks**: writer bumps `seq` to odd, writes
  payload, bumps to even; reader snapshots `seq`, copies, re-reads `seq`,
  retries on mismatch/odd. Bounded retries, then the staleness path. No
  lock means a killed child can never leave a reader deadlocked.
  *Memory-ordering caveat documented in the module:* pure Python provides
  no fences; the protocol is sound on x86-TSO (the deployment rig) and the
  synchronous tests don't exercise the race. If arm64 robots ever matter,
  revisit (double-buffer + published index, or payload checksum).
- **View discipline (BufferError-proof):** all numpy views over `shm.buf`
  are per-read, copied out, and dereferenced before returning — no cached
  views anywhere, or `SharedMemory.close()` raises `BufferError: cannot
  close exported pointers exist`. `close()` on the reader drops any
  transient state before `shm.close()`.
- `published_s` is child-stamped `time.monotonic()` — boot-relative and
  machine-wide on both Linux and macOS, so the parent's existing staleness
  comparison carries over. (Implementation-defined rather than
  contractual; documented at the stamp site. A frozen test clock on the
  parent side against real child stamps yields a large *negative* age,
  which correctly passes `<= MAX_FRAME_AGE_S` — commented so nobody
  "fixes" it.)

### 3. Parent-side `_ProcessRealsenseCameraReader`

Drop-in replacement constructed where `_RealsenseCameraReader` is built
today (`YAMEmbodiment.__init__`), same public surface:

- `__call__(cfg)` → colour from shm, `cv2.resize` to `cam_{width,height}`
  (cv2 stays a lazy parent-side import).
- `extra(cfg)` → `{name}_intrinsics` as a plain rescaled array;
  `{name}_depth` as a **thunk** that re-reads the shm slot at resolution
  time — preserving the documented "fresh conversion of the newest
  captured frames" contract. **Thunk order of operations:** check reader
  generation and closed flag *first* (raising the existing "resolved after
  camera close or reopen" `RuntimeError`), only then construct views —
  never let a stale thunk surface as `BufferError`/`ValueError`.
- The staleness loop (constants reused from the inline reader:
  `MAX_FRAME_AGE_S = 0.5`, 10 × 50 ms) additionally checks
  `child.is_alive()`; a dead child surfaces as the existing
  `frame read failed for {name}` fault shape.
- Reopen restarts the child, creates fresh shm blocks, and bumps the
  generation; outstanding thunks from the prior generation fail with the
  generation error, exactly as today.
- The inline `_RealsenseCameraReader` **remains** the semantics reference
  and the `realsense_capture=inline` implementation; shared constants are
  reused, not redefined.
- `YAMEmbodiment._builtin_realsense_reader`'s annotation widens to a
  shared protocol (`__call__` / `extra` / `close`) so mypy strict accepts
  either reader; the process reader gets its own injectable seam (child
  entry + transport) for tests.

### 4. Config: `realsense_capture` mode + `depth_fps`

- `realsense_capture: str = "process"` — `"process"` (new default) or
  `"inline"` (the current in-process reader, kept as the debugging escape
  hatch). Validated in `__post_init__` with a guided error naming both
  values.
- `depth_fps: int = 30` — threaded into **both** readers' `enable_stream`
  calls (colour and depth locked to the same rate), so
  `realsense_capture=inline` + `depth_fps=15` does what it says.
  Range-validated (1–90, int); invalid device combinations still fail at
  open with the librealsense error, propagated cleanly by the handshake.
  Capture *resolution* stays 640×480 and out of scope (plan 0011's
  standing exclusion); the K-rescale denominators become named constants
  shared by `_open_one` and `extra()` so a future resolution change is one
  edit.
- **Adjacent papercut from #95 — guided error, not coercion:** a
  `{slot}_depth_serial` arriving as `int` (config.ini digit strings are
  int-coerced by core `_parse_value`) now raises a guided `ValueError`
  in `from_kwargs`: *"quote the serial in config.ini — numeric values are
  int-coerced and lose leading zeros."* Silent `str()` coercion is ruled
  out: `int("038...")` has already destroyed a leading zero by the time we
  see it, and a silently-wrong serial fails at open with a
  one-invisible-character diff — worse than the crash. `health.py`'s
  `_RAW_STRING_KEYS` workaround stays.

### 5. Out of scope

- V4L2 path: untouched (never implicated).
- `health.py` / `watch.py` RealSense coverage: V4L2-only today; teaching
  them the process reader is follow-up work (noted in #95).
- Capture resolution overrides (plan 0011's exclusion stands).
- i2rt-side retry tolerance (upstream hardening).
- Core `_parse_value` changes.

## Behavior changes on upgrade

- RGB-only rigs: none (no RealSense slots → no child process).
- RGB-D rigs: capture runs in a spawn child by default; observation
  contract, staleness budget, error shapes, and thunk semantics unchanged.
  `-E realsense_capture=inline` restores the old wiring (including its
  in-process GIL contention — that's what the escape hatch is for).
- A second Python process exists while a depth rig is open (visible to
  `multiprocessing.active_children()`; OS process title is the standard
  spawn command line).
- Int depth serials now fail fast with a quoting hint instead of
  `AttributeError`.

## Tests

All hardware-free, preserving the 100% branch gate. The only pragma in new
code is the child's real `import pyrealsense2` line.

1. **Seqlock + layout**: writer/reader round-trip over a real
   `SharedMemory` block; torn-read retry (odd seq); bounded-retry
   exhaustion → staleness path; view discipline (close succeeds after
   reads — no `BufferError`).
2. **Child logic in-process, for coverage**: `_child_main` driven with
   `FakeRs` + a real `Pipe` + real `SharedMemory` in the test process —
   serial resolution, dup rejection, all-or-nothing open, warm-up,
   publish, stop via Event, **exit on Pipe EOF** (parent-death path),
   tracker-unregister call. This is how the entry meets the branch gate
   without wholesale pragmas.
3. **True-subprocess lifecycle** with a **fake child entry** (test helper
   writing synthetic frames into shm), children started with coverage
   disabled (env guard) so kill-escalation tests can't corrupt coverage
   data: ready/error/timeout handshake; staleness raise on silent child;
   dead-child detection; close/join/terminate escalation; reopen after
   kill attaches fresh blocks (the resource_tracker regression test).
   (Subprocess-in-tests precedent: `test_collision.py`.)
4. **Reader parity**: `_ProcessRealsenseCameraReader` produces identical
   images/extra shapes, K rescale, thunk freshness/generation errors as
   the inline reader given the same synthetic frames.
5. **Config**: mode validation, `depth_fps` bounds and inline-reader
   threading, int-serial guided error (the #95 crash becomes a passing
   test asserting the hint text).
6. **Existing embodiment tests**: the current RealSense embodiment tests
   (`builtin_embodiment()` and friends in `test_depth_reader.py`) pin
   `realsense_capture="inline"` — they test inline semantics through the
   in-process `_import_rs` monkeypatch seam, which cannot reach a spawned
   child. The `isinstance(..., _RealsenseCameraReader)` assertion stays
   valid under the pin. New process-mode embodiment tests use the fake
   child entry.
7. **Fake promotion, scoped**: exactly `FakeRs`, `FakePipeline`,
   `FakeDevice`, `FakeContext`, `FakeAlign`, `FakeConfig`, `FakeFrame`,
   `FakeFrameset` (+ the `frameset` helper) move from
   `test_depth_reader.py` to `conftest.py`. The cv2/capture fakes do
   **not** move — `conftest.FakeCapture`/`FakeCv2` (caps-dict contract,
   used by camera/health/watch tests) and `test_depth_reader`'s local
   same-named classes (auto-creating contract) are different animals; the
   local ones stay local. The colliding `Clock` stays deduped
   deliberately.
8. **On-rig acceptance (operator, post-merge)**: the #95 repro — a
   3-camera depth episode survives homing + first observation; re-measure
   plan 0011's `## Measurement` contention baseline.

## Implementation tasks

Ordered; each lands with pytest + mypy strict + ruff + 100% coverage green.

1. Config fields (`realsense_capture`, `depth_fps` incl. inline reader
   threading) + int-serial guided error + validation tests.
2. Shared-memory slot + seqlock + lifetime protocol (`_capture_proc.py`
   data plane) + unit tests.
3. `_child_main` (rs-injectable, Pipe-EOF exit, tracker unregister) +
   in-process tests with FakeRs; promote the rs fakes to `conftest.py`.
4. Parent handshake/lifecycle (spawn, unlink-after-ready, join/terminate
   escalation, daemon flag) + fake-entry subprocess tests with the
   coverage env guard.
5. `_ProcessRealsenseCameraReader` + parity tests + reader protocol +
   `YAMEmbodiment` wiring behind `realsense_capture` + inline pins in
   existing tests.
6. Docs: config comment blocks, CLAUDE.md capture-architecture note,
   CHANGELOG entry.
